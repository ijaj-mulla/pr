# System Design Answers

These answers refer to the architecture used in the submitted frontend and distinguish current implementation details from production extensions where the current browser-only implementation does not have a backend or real robot connection.

## 1. What happens if we ask you to add a new feature to this later? Does your current design accommodate that, or does it need a rework? Walk through a specific feature and where it would plug in.

A realistic future feature would be **task assignment and management**. Operators could assign tasks to robots, track task progress, and reassign work when a robot becomes unavailable. The current design can accommodate this without a major UI-state rework because fleet state is centralized in `src/store/fleetStore.ts` and both replay and live simulation already pass through the same update path. I would extend `RobotState` in `src/types/index.ts` with fields such as `current_task_id`, `task_start_time`, and `task_status`. A new `TaskManagement` component could sit alongside the existing `FleetSummary` and `RobotSearch` components, while `src/components/RobotMap.tsx` could display task indicators on robot markers. Task updates would be handled through the same centralized store so the map, details, and summary views remain consistent.

## 2. What happens if the number of robots grows a lot, say from eight to five hundred? What is the first thing that breaks, and why that specifically?

The first likely bottleneck would be browser rendering performance in `src/components/RobotMap.tsx`, because the current implementation renders robot markers as DOM elements. This is appropriate for the required eight robots but could become expensive when hundreds of markers update frequently. A second bottleneck would be the current `calculateFleetActivityOverTime` implementation in `src/lib/fleetUtils.ts`, which processes robot events across time intervals and would become more expensive as robot count and history length grow. To scale toward 500 robots, I would move map rendering toward canvas or another rendering approach designed for many frequently updated markers, and optimize fleet-level calculations through incremental updates or server-side aggregation. Zustand could remain useful, but the state representation and update frequency would need to be tuned for the higher event volume.

## 3. What happens if bandwidth is limited and robots and the backend can only exchange a small amount of data per second? What would you change about what you send, how often, or how much detail it carries?

For a bandwidth-constrained production system, I would send only the fields needed for the current state: `robot_id`, position `(x, y)`, status, battery, and the event time/order value `t`. Static information such as `robot_type` could be sent during initialization rather than with every telemetry update. Task events should be event-driven rather than repeated with normal position updates. I would also reduce the telemetry frequency when appropriate, for example toward 1–2 second intervals, and prioritize immediate transmission of important state changes such as `error`, `blocked`, or `offline`. The current `RobotEvent` model already centers on the small set of fields needed by the dashboard, and the 1-second `LiveSimulator` interval provides a baseline that could be adjusted for network conditions.

## 4. What happens if a robot goes down mid task and stops responding? What should the rest of the system do about it, and how would it even find out?

The current implementation is browser-only and does not have a real robot connection or heartbeat mechanism, so it cannot independently detect an actual network failure. In a production version, the backend would detect a robot as stale when no heartbeat or telemetry update arrives within a configured timeout. It would mark the robot as offline and publish that state to connected clients. The existing frontend attention classification in `src/lib/fleetUtils.ts` and the robot filtering UI in `src/components/RobotSearch.tsx` could then surface the problem to the operator. If the robot had an active task, a task-management service could identify the interrupted task, determine what work remains, and make it eligible for reassignment to an available robot. `RobotDetails` could show the last known position and state so the operator has enough information to decide on recovery.

## 5. What happens if the connection between a robot and the backend is slow or unreliable, and updates arrive late, out of order, or not at all for a while? What does the rest of the system see during that time, and how does it recover once the connection is healthy again?

The current frontend simulator does not receive updates over an unreliable network, so this behavior is a production extension rather than an existing network implementation. In a production telemetry path, each robot update would carry an ordering value such as the event's `t` value (or, preferably for a real system, a server-side timestamp/sequence number). The backend or client state layer would reject an update that is older than the latest accepted update for that robot. During a temporary gap, the dashboard should keep displaying the last known position and status while indicating that the data is stale, rather than pretending the robot is still reporting normally. Once connectivity is restored, the backend/client connection should resynchronize from authoritative current state and, where required, replay missed events from durable history. The existing `updateRobotState` function in `src/store/fleetStore.ts` provides the centralized place where timestamp/sequence validation could be added.
