# System Design Answers

## 1. Future Feature
One realistic future feature would be **task assignment and management**. This would allow operators to assign specific tasks to robots, track task progress, and reassign tasks when robots go offline or encounter errors. In the current architecture, this would plug into the existing `RobotState` type in `src/types/index.ts` by adding fields like `current_task_id`, `task_start_time`, and `task_status`. The `RobotMap` component in `src/components/RobotMap.tsx` could be extended to display task indicators on robot markers, and a new `TaskManagement` component could be added to the left panel alongside `FleetSummary` and `RobotSearch`. The centralized fleet store (`src/store/fleetStore.ts`) would handle task state updates, ensuring consistency with the existing replay and live event paths.

## 2. Scale from 8 robots to 500
The first likely bottleneck at 500 robots would be the browser's rendering performance when displaying all robot markers simultaneously on the map. The current implementation in `src/components/RobotMap.tsx` renders every robot as a DOM element, which works well for 8 robots but could cause performance issues with 500. Additionally, the current `calculateFleetActivityOverTime` function in `src/lib/fleetUtils.ts` iterates through all robot events at each time interval, which would become computationally expensive with more robots and longer time windows. To scale to 500 robots, the architecture would need canvas-based rendering or virtualization for the map, and the activity calculation would need to be optimized (e.g., pre-computed on the backend or using incremental updates). The state management approach (Zustand) would still work, but the volume of events would require more efficient data structures and potentially server-side aggregation.

## 3. Limited Bandwidth
With limited bandwidth, the system should send compact robot updates containing only the essential fields: `robot_id`, `position` (x, y), `status`, `battery`, and `timestamp`. These updates should be sent at a reasonable frequency (e.g., 1-2 seconds) rather than continuously. Lower-value fields like `robot_type` (which is static) could be sent only once during initialization, and `task_event` could be sent only when a task-related event actually occurs (e.g., task_completed, task_failed). The current `RobotEvent` type in `src/types/index.ts` already includes these core fields, so the data model is well-suited for bandwidth-constrained scenarios. The `LiveSimulator` in `src/lib/liveSimulator.ts` generates events at 1-second intervals, which is a reasonable baseline that could be adjusted based on network conditions.

## 4. Robot Down Mid-Task
When a robot goes down mid-task, the system should detect the failure through stale or missing heartbeats (no updates received within a timeout period). The fleet store (`src/store/fleetStore.ts`) would mark the robot's status as `offline` or `error`, and the operator would be alerted via the attention filter in `src/components/RobotSearch.tsx`. The system should identify the affected task by checking the robot's `task_event` field and determine whether the task was partially completed. Remaining work should be reassigned to available robots (those with status `idle` or `active`). The `FleetSummary` component would reflect the updated attention count, and the operator could use the `RobotDetails` component to review the robot's last known position and status before deciding on recovery actions.

## 5. Slow/Unreliable Connection
To handle late, out-of-order, and missing updates, the system should use timestamps (the `t` field in `RobotEvent`) to determine the most recent state for each robot. When updates arrive out of order, the system should discard stale updates (those with timestamps older than the current known state) and apply only the most recent data. For missing updates, the system should tolerate gaps and continue displaying the last known state rather than showing errors. When the connection becomes healthy again, the system should resync by requesting the current state of all robots. During stale data periods, the operator would see the last known robot positions and statuses, but the UI could indicate data staleness (e.g., a timestamp showing "last updated X seconds ago"). The current `updateRobotState` function in `src/store/fleetStore.ts` already handles state updates atomically, and adding timestamp-based conflict resolution would be a straightforward extension to this logic.
